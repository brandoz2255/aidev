# Harvis UI recon — what's missing & what to build (2026-07-18)

## Executive summary

Harvis already has an unusually deep surface inventory — a 2,456-line composer with slash commands, voice call mode, and a per-model effort slider; a full Build cockpit; Agent Studio with run inspection; notebooks; a skills manager; and user-memory CRUD. The gaps are therefore not "missing features" but missing *connective tissue*: (1) there is no true command palette — `SearchModal` searches chat content only, while every competitor converges on keyboard-first action surfaces; (2) the Projects/Spaces container (chats + files + instructions + scoped persona in one folder) is now table stakes across ChatGPT, Claude, Perplexity, and Manus, and Harvis's `harvis/projects` route exists but its depth against that pattern is unverified; (3) the converged long-run trust pattern — agent-maintained visible checklist + linked session log + notify-on-done — is partially present (PlanPanel, WorkflowInspector, OWUI-heritage browser notifications) but not wired into one coherent loop; (4) the mascot system is halfway to being a genuine run-state instrument but currently shows only 3 of 7 real run states and auto-waves over finished output. Honest negatives: cloud sharing, real-time collaboration, and a mobile-native app matter little for a self-hosted, local-first tool and should not be built now. **Top recommendation: ship the mascot-as-run-state-instrument (Option 1 below) first** — it is ~1 day of pure frontend work, fixes verified accessibility and correctness gaps (`talking` unimplemented, done-runs waving forever, no `prefers-reduced-motion`), and delivers the "live presence in every session" feel at the lowest risk — then follow with the command palette and the Projects container upgrade.

## Proposed UI options (ranked)

Ranked by value-per-effort. "FE" = pure frontend; "BE" = backend work required.

1. **Mascot as run-state instrument** (FE, S — ~1 day). Extend `HarvisClawMascot.svelte` to a full pose vocabulary mapped 1:1 to `runStages.ts` stages; drive `RunView.svelte:204` and `WorkspaceRunCard.svelte:489` from stages instead of the coarse `running` boolean; implement the missing `talking` branch; kill the idle auto-wave for done runs; add `prefers-reduced-motion` guards. Fits Harvis because run surfaces are its identity and the components already ship. Conflicts with nothing; fixes verified bugs. Detail in the mascot section below.

2. **Command palette** (FE, M). New `CommandPalette` component invoked from the existing global keydown handler in `routes/(app)/+layout.svelte`, merging: route jumps (all `harvis/*` surfaces + `surfaces.ts` registry), the existing shortcut actions, settings tabs, and existing `SearchModal` chat search as a mode. Fits Harvis because surface count has outgrown the sidebar. Partially replaces `SearchModal` as the entry point (keep it as the search mode); `ShortcutsModal.svelte` becomes the palette's cheat sheet.

3. **Wire notify-on-done + ambient sidebar mark** (FE mostly, S–M). Subscribe an animated variant of `HarvisLogoMark` (`Sidebar.svelte:859,1072`) to a derived "any run active" store over the existing `runStream.ts` per-run SSE store: antenna breathe while active, one blink-smile on done, red flick on fail, steady-bright on awaiting-approval; plus fire the existing browser `Notification` on background-run completion. This is mascot Option 2 and the honest local analogue of ChatGPT/Gemini task notifications. Composes with #1 (shared state mapper). Flag: whether notifications are currently wired to run lifecycle is unverified — check before building.

4. **Projects container upgrade** (BE + FE, M–L). Bring `harvis/projects/[id]` (`routes/(app)/harvis/projects/`) to the Projects/Spaces shape: scoped chats list, attached knowledge (reuse `lib/apis/knowledge` + K3 pipeline), and per-project instructions injected into chats. Fits Harvis because the ingredients (folders, knowledge, memories CRUD) all exist but are unscoped. **Audit the current projects page first** — its existing depth is unverified. Conflicts with sidebar Folders — decide whether folders and projects merge or coexist before building.

5. **Local/cloud usage page** (BE + FE, M). New Agent Studio surface registered in `lib/agent-studio/surfaces.ts` ("Usage"), aggregating what `UsageMeter.svelte` already computes per-run into an account-level view split local-Ollama (free pool) vs cloud engines (paid pool), Cursor-style. Fits Harvis's multi-engine identity directly. Needs a backend aggregation endpoint over run/usage records. Per memory: never fabricate provider quota bars — show only measured tokens/cost.

6. **@-mention engine mid-thread** (FE + small BE, S–M). Extend the composer's existing `Commands/` Models command (`MessageInput.svelte`) so `@engine/model` routes just that message to the named engine, rendering via the existing `MultiResponseMessages.svelte` compare infra when multiple are mentioned. Fits the engine/model split Harvis already has everywhere (Build, Discord). Verify current Models-command behavior first — mid-thread summon may partially exist.

7. **Run replay** (FE, M — assuming events are persisted). "Replay" button on finished runs in `RunView.svelte` / `WorkflowInspector`, stepping through the recorded event stream with the timeline the inspector already renders. High trust value, near-zero new data model *if* run events persist server-side — **verify persistence before committing**.

8. **Selection-targeted edit in artifacts** (BE + FE, M). Select text/code inside `Artifacts.svelte` / `CanvasRenderer.svelte` → floating "edit this" affordance → scoped edit request instead of full regenerate, plus 2–3 Canvas-style shortcut buttons (fix bugs, tighten, polish). Fits the existing typed-canvas contract (`chat_completion.py` per memory). Backend needs a targeted-edit path; highest implementation uncertainty on this list.

9. **Guided empty states** (FE, S). Perplexity-style "Add sources → Add instructions" affordances on empty knowledge/project/notebook views, reusing `Placeholder/` variants (FolderKnowledge etc.). Cheap onboarding win; do it opportunistically alongside #4.

## Session mascot concept

Three ranked options (full grounding: `front_end/owui/src/lib/components/common/HarvisMascot.svelte`, `HarvisClawMascot.svelte`, `HarvisLogoMark.svelte`; call sites `Placeholder.svelte:197`, `RunView.svelte:204`, `WorkspaceRunCard.svelte:489`, `Sidebar.svelte:859,1072`).

**Option 1 (recommended) — the run-state instrument.** Make the claw mascot *the* status display, Copilot-glyph style: thinking = eye-scan + antenna pulse; streaming = finally-implemented `talking` mouth; tool-running = existing `working` claws; awaiting-approval = frozen raised claw (stillness = "waiting on you"); done = one-shot `wave` then static smile (no idle cycle); failed = `angry` decaying to a new drooped-antenna sad pose; cancelled = neutral static. Driven by a ~30-line `stage → mascotState` mapper over `runStages.ts` output. Gimmick risk low — every motion carries state the UI needs anyway. Cost ~1 day.

**Option 2 — the wake-up mark.** The sidebar `HarvisLogoMark` becomes the cross-session ambient presence (the only truly "all sessions" surface): CSS-keyframe antenna glow while any run is active (fed by `runStream.ts`), one blink-smile on done, red flick on fail, steady-bright for awaiting-approval. Three signals only — finer distinctions are illegible at 24px. Mind the duplicate-SVG-id hazard documented in LogoMark's own header comment. Cost 1–2 days. Composes with Option 1 — doing both is the coherent full concept: instrument up close, ambient at the edge.

**Option 3 — cameo moments.** Full-body `HarvisMascot` only at emotional beats (empty states, failures, cold-load waits, long-run completion) — the Discord-Wumpus model. Highest gimmick risk (this is the lane Clippy lived in); completion toasts need notification plumbing that doesn't exist yet. Do last, if at all.

**Do-not-do list (binding):** no proactive speech bubbles/tips ([Clippy lesson](https://thenewstack.io/humanity-vs-clippy-lessons-from-microsofts-failed-virtual-assistant/)); no animation over finished content the user is reading (today's real offender: `RunView` idle auto-wave every ~12s on done runs); no mascot per-message; no motion ignoring `prefers-reduced-motion` (both mascots' rAF loops currently do — fix first, per [WCAG 2.2.2](https://www.w3.org/WAI/WCAG22/Techniques/css/C39) and [web.dev](https://web.dev/learn/accessibility/motion)); no focus-stealing or modals; no guilt/streak notification personality ([Duolingo cautionary tale](https://www.lookatmyprofile.org/blog/rip-duo-how-duolingo-s-psycho-owl-mastered-digital-manipulat-1756688542085)); no two mascots animating on one screen; no duplicate SVG filter/gradient ids; no fake states — never show `working` claws when nothing executes; stop the rAF loop for static poses and hidden tabs.

## Recommended sequence

1. **First: mascot instrument + reduced-motion fix** (proposal #1 / mascot Option 1). Smallest, purest, fixes verified defects, and delivers the "alive" feel the session was asked for. One day, pure frontend, zero conflict.
2. **Second: command palette** (proposal #2), then **ambient mark + notify-on-done** (proposal #3) — together these make the breadth of Harvis discoverable and its background work visible, the two cheapest trust wins.
3. **Third: Projects container audit-then-upgrade** (proposal #4), with guided empty states (#9) folded in. Audit `harvis/projects/[id]` before writing code — its current depth is unverified. Usage page (#5) and @-mention (#6) follow as capacity allows; replay (#7) after verifying event persistence; selection-edit (#8) last among the builds.

**Explicitly do NOT build:** real-time collaboration/presence, a mobile-native app, a hosted artifact-publishing service, cloud push/email notification infrastructure, user-editable keybindings (defer), and mascot cameo toasts (Option 3) until the notification plumbing exists and Options 1+2 have proven the character earns its screen time.
